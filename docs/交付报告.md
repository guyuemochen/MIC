## 评审发现

状态说明：**verified** = 已由实跑复现确认，且修复后通过验收回归（2 个高危问题均已修复）；**unconfirmed** = 评审判断附证据，未经独立复核、未修复。

### 已确认并修复（高危）

#### 1. [high · verified] milp/src/simplex.rs:485 — 热启动修复判定有洞

**问题**：resolve() 热启动修复判定有洞：上一调用以 Infeasible 结束（Phase-1 最优、人工变量带正值留基）后，snap 传播可把该人工变量基值精确推到 ≤ tol.feasibility，basics_violated() 判 false 跳过 Phase-1 修复，Phase-2 在等式行被零成本人工变量吸收的错误 LP 上求解，终检降级为 IterationLimit，分支定界将其记为 limit_hit，对可解问题谎报 LimitReached。

**证据**：读取 resolve()（simplex.rs:463-492）与 basics_violated()（1386-1406，人工变量仅查 |rhs|>feas）。临时工程（path 依赖 milp，未改 crate）实跑复现：max 5x1+5x2+5c s.t. 5x1+4x2+c=4, 2x1+2x2+0.5c≤6.5，x1,x2∈[0,5] 整数，c∈[0,3]。warm 序列 root→x2≤0→(x2≤0∧x1≤0: Infeasible)→(x2≤0∧x1≥1: Infeasible) 后，兄弟节点 x2≥1 直接 resolve 得 `IterationLimit ... x=[1.5,1,3]`，同一界冷启动 `Optimal obj=5.000000 x=[0,1,0]`。状态转储显示 n3 末态 basis=[col4(art),col3]、art 值 0.2；snap 传播 0.2−(−1)(−1)−(1)(−0.8)=0.0 精确为零 → basics_violated=false → 跳过 Phase-1；随后 Phase-2 两次主元后 art 涨到 2.1（等式行被人工列吞掉）、终检降级 IterationLimit。端到端 solve()（关割/关启发式）：`LimitReached obj=None nodes=5 iters=8`，而真最优 5.0（默认选项因割改变树形恰好绕开，同一 fuzz 另一算例 iter157 同样命中，真最优 4.0）。仓库内 test_warm_recover_after_infeasible_node 规模过小未覆盖此形态。dive 后 branch_bound.rs:207 的根恢复 resolve 同样暴露于此路径。

#### 2. [high · verified] planner/src/format.rs:256 — CAP 糖在 RES 交错时写错资源

**问题**：CAP 糖在首个 CAP 之后出现过 RES 时，把容量写进最后一个资源（可能是 RES 刚建的资源）而非 "cap" 资源——静默产生错误模型。

**证据**：CAP 分支用 `resources.last_mut().expect("cap resource just created")` 定位 cap 资源，该假设仅在"cap 是最后一个资源"时成立；而模块文档 format.rs:10-11 规定七类指令"任意交错均合法，唯一强约束 RES/CAP 先于 DEMAND"，故 `CAP → RES → CAP` 是合法排布。实测（独立验证 crate，path 依赖 planner，未改动被评 crate）：输入 `VALUES 2 / ENTITIES 1 / CAP 0 5 / RES gpu 7 7 / CAP 1 3`，解析结果为 cap=[5, 4611686018427387903(哨兵)]、gpu=[7,3]，断言 `gpu == [7,7]` 失败——`CAP 1 3` 覆盖了 gpu 的容量而非 cap 的。对照场景（CAP 全在 RES 前）结果正确。README:80 与 format.rs:18-19 的 normative 语义均为"后续 CAP 行复用同一资源(cap)"。无任何错误抛出，模型静默错误→求解结果错误。已 grep 确认 6 个发货算例无一混用 RES+CAP，故验收测试未暴露。

### 未复核待定（中低危）

#### 3. [medium · unconfirmed] milp/src/cuts.rs:363 — 割后根 LP 不可行误判为数值错误

**问题**：cut_loop 把割后根 LP 不可行一律判为 Err(Numerical)（"理论不可能"），但整数不可行问题的有效 GMI 割本就可把 LP 区域切空，正确终态是 Infeasible 而非报错。

**证据**：模块文档（cuts.rs:326-329）同样断言"割循环中 LP 变 Infeasible 理论不可能"——该断言只对存在整数可行解的问题成立。默认选项（SolveOptions::default()，即 CLI 生产路径）600 次随机小规模 MILP 差分 fuzz：8 例返回 `Err(数值异常：割循环后根 LP 不可行：割错误地切掉了全部整数可行解（理论不可能，判定为数值异常）)`，穷举全部整数点证实每例真值均为 Infeasible（如 max 6x1+2x2+5c s.t. 2x1+5x2+2c=8, 3x1+3x2+0.5c≤3.5，x1∈[0,5],x2∈[0,2] 整数：0 个整数可行点）；关割运行对同一问题在 5 节点内正确报 Infeasible。CLI 表现：退出码 1 + `error: 数值异常...` 而非退出码 2 + `status = infeasible`。

#### 4. [medium · unconfirmed] milp/src/simplex.rs:629 — add_row 列下标与人工列段撞号

**问题**：add_row 给新割松弛列分配下标 n+layout.slack.len()，与上次 rebuild_initial_basis 已占用该段的存量人工列（ncs+t）撞号：num_art>0（任何 Eq 行或在 x⁰ 处违反的 Ge/Le 行）时调 add_row，新割松弛列与旧人工列共用同一列下标，表格不再是 B⁻¹A、layout.slack 错误认领该列。

**证据**：读 add_row：`slack_col = n + self.layout.slack.len()`（628-637）与 rebuild_initial_basis 的 `art_col_of_row[i] = ncs + t`（875-886）共享同一下标段。公开 API 探针实跑（1 Eq + 1 Le 问题，根解后 basis=[0,2]）：add_row 后 `basis=[0,2,3]`，新割基列 3 恰为 Eq 人工列的居住下标；表格列 3 在旧行保留人工列数据、新行写松弛系数，matrix≠B⁻¹A。183 次"满足型加行"差分 fuzz（warm resolve vs 割写成原生约束的冷解）与 295 次端到端 MILP fuzz（割开/关 vs 穷举真值）均零错值——crate 自身管线里割恒违反（violation≥1e-7>feas）⇒ 人工列入基 ⇒ 下次 resolve 必触发修复性 rebuild 从 row_terms/row_slack 记账重建表格，脏数据被丢弃；这是靠修复路径偶然兜住的不变量破坏，add_row 文档明示允许任意加行（"当前解可能违反新行，由随后 resolve 修复"），任何后续改动（批内满足型割、修复触发条件变化、外部调用者）都可使带脏数据的列进入定价。

#### 5. [medium · unconfirmed] planner/src/localsearch.rs:223 — tabu_size 极大值加法溢出

**问题**：`tabu_until[ents[i]] = steps + tabu_size` 在 tabu_size 取极大值（如 usize::MAX）时加法溢出：debug 构建 panic，release 构建回绕为 0 使禁忌静默失效；入口校验只拦 `tabu_size < 1`。

**证据**：实测：以 lib 公共 API 配置 `TabuSearch { tabu_size: usize::MAX }`、Steps(3) 跑 local_search——debug 构建在 `D:\projects\others\MIC\planner\src\localsearch.rs:223:47` panic `attempt to add with overflow`（第 1 步成功应用移动后，第 2 步 1 + usize::MAX 溢出）；release 构建回绕为 0，实体立即恢复可采纳，禁忌机制静默失效（跑完 steps=3 无报错）。入口校验（localsearch.rs:131-135）仅要求 ≥1，与 crate 声明的"入口校验配置杜绝 history_len=0 类 panic"（lib 设计意图、localsearch.rs:113-119 文档）同类缺口。CLI 未暴露 tabu_size，故仅 lib API 可达。
