# 稠密引擎第二阶段数值失败的一次冷恢复设计

审查基线：主线 `60da4b9`，相关 MILP 代码树与 `c289c77` 一致。本次为只读设计审查，没有修改生产文件，没有编译或启动求解。后续主线诊断提交若不修改求解代码，不影响下述定位。

## 结论与实施范围

可以在同一次 LP 调用内安全尝试一次冷恢复，但静态审查不能保证它能救回 lseu。第一版只覆盖 Dense 的本轮 `PhaseOutcome::Failed` 第二阶段出口，且当前没有 Phase-1 欠账。不能根据跨调用的 `numerical_error: Option<String>` 决定恢复，不能根据字符串内容识别阶段，更不能把真正的迭代、工作步或时间上限当作可恢复数值失败。

恢复复用当前实例的 `rebuild_initial_basis` 与既有完整两阶段流程；当前变量界、全部原行和割行、目标及行映射保持。新流程必须重新走完原有证明检查，不复用失败前的目标、解、对偶或原始可行性结论。再次数值失败或重建后证明未完成仍按原状态返回，B&B 的未决子树和 `limit_hit` 粘滞规则完全不改。

## 已确认的代码路径与尚未确认的根因

`simplex.rs::primal_step_is_safe`（约 1807 行）对非离基行计算 `rhs - (delta*t)*a`；`do_pivot_legacy_inner` 与 `do_pivot_nz` 均以未改写的入基列系数做同顺序的 `rhs -= delta*t*fk`，离基行改为进入变量旧端点加 `delta*t`。没有发现这两条实际更新把同一个 rhs 重复扣减的问题。界翻转的预检和执行均用端点差，也一致。

`run_phase`（约 2175 行）在每 200 个原始单纯形主元之后调用 `refresh_values`（约 2330 行），随后才检查全界。刷新改用 `binv * (row_rhs - N*x_N)` 重算全部 rhs，不受刚才对增量更新的步前预检覆盖。这是独立的浮点计算路径：其中 `binv` 本身也由历次表格消元累积维护，刷新并不是重新从基矩阵因子化得到的“精确基真值”。它既可能揭露增量 rhs 漂移，也可能带来累积逆矩阵及乘加误差。因此，安全比值与刷新后超界并不矛盾，不能用放宽界容差解决。

刷新计数在 `start_call` 归零，只在阶段主循环 Leave 分支增加；对偶修复、人工清理的主元虽计入 `iter_call`，不增加该刷新计数。故即使取得调用迭代数，也不能只看它是否整除 200 判断故障来源。

同一个“阶段 2 行 … 超出绝对界容差”错误还用于 Phase-2 入口检查，入口可能承接 snap、对偶修复或人工清理。对当前量级约 1、超界约 `8.2e-7` 的有限值，若活动上界确为 1，普通加减 feasibility 的舍入差不能解释如此大的偏离；但现有记录仍缺少实际基列、界值、检查位置和刷新前后值，不能把“刷新最可疑”写成已确认。

已读诊断说明：lseu 的 effective_engine 为 tableau，原始上下文为 89 个变量、28 行；两条失败只有 stage/status/message/pending，没有各自调用的迭代数和失败位置。相邻成功 LP 的 303 次迭代不能嫁接到失败事件。错误内部行号 74 也提醒恢复必须保留故障 LP 的现有行集合，不能重新用原 Problem 构造一个丢割的引擎。

如需下一步精确定位，最小只读诊断记录应放在原有失败点，包含入口/普通步后/刷新后标签、phase、iter_call、pivots_since_refresh、basis[row]、lb/ub、刷新前后该行值。无须改变计算顺序或阈值，也不必为了定位先增加恢复循环。

## 推荐的最小私有接口

保留外部 `solve`、`resolve`、`resolve_with_work_limit` 及 `LpEngine` 签名。推荐把现有 `run_two_phase_with_limit` 的主体抽为“一次尝试”私有函数，仍返回原 `LpStatus`，另借一个局部布尔输出 `phase2_numerical_failed: &mut bool`：

1. 一次尝试入口把输出置 false；所有现有 Phase-1、清理、限额、不可行、无界及正常最优出口都保持 false。
2. 只在最后 `run_phase(2, work)` 的 `PhaseOutcome::Failed(msg)` 分支置 true，照旧设置诊断并返回 `IterationLimit`。
3. 原 `run_two_phase_with_limit` 成为薄包装：执行第一次尝试；非本轮 Phase-2 数值失败、状态不是 IterationLimit 或 `phase1_pending` 为 true 时直接返回。
4. 通过恢复前预算检查后，仅重建一次，立新人工欠账，再检查预算；随后直接调用“一次尝试”函数第二次并返回，第二次绝不能回调恢复包装。

这样只有两个显式尝试，没有递归、while 重试、新持久字段或新的隐式循环。也可用局部私有结果类型表达同一事实，但无需扩展公共状态枚举。原有入口三处调用收口可保持；普通 `solve`、首次 `resolve` 和热 `resolve` 都共享最多一次额外失败恢复。冷启动自身失败后重试可能重复同一路径，只是有界的额外成本，不能保证改善。若未来需缩窄到纯热状态，需另立证据，不应悄悄按算例选择。

诊断字符串只用于解释。普通非 proof_profile 构建目前不会在每个公开调用入口清空旧诊断，所以 `IterationLimit && numerical_error.is_some()` 存在误把旧错误当新错误的风险，局部资格标志能彻底避免。决定真正进行第二次尝试时，可以清除第一次数值诊断，让第二次的真实失败原因或真实上限成为最终诊断；这不清除 Phase-1 欠账，也不清除任何资源统计。若在重建前后发现额度已尽而未开始第二次尝试，可保留第一次数值原因辅助解释，但状态必须按真正停止原因返回。

`build_solution` 的终检降级、非法 bounds、构造时不可行标记、Phase-1 失败均不属于本次恢复入口。不要扩大到所有返回 IterationLimit 的公开调用。

## 预算、人工欠账与终止

恢复前必须检查同一个 `LpWorkLimit` 尚能开始一个真实步骤、`iter_call` 尚低于原调用的有效迭代限额、原绝对 deadline 尚未到期。限额公式必须与 `run_phase` 完全一致：`max(10_000, 20*(m+n))`，有 hint 时按现有 `hint.max(1_000)` 规则；推荐抽一个纯私有只读限额函数供两处共用，不能在恢复时发放“剩余新 hint”。检查顺序沿用现有工作额度、调用迭代、期限的优先级；恢复失败路径额外读钟只在 deadline 为 Some 时发生，None 时仍零读钟。

不得调用公开 `solve/resolve`，它们会 `start_call` 并重置调用计数与反循环状态；也不得新建引擎。`iter_call`、`iterations_total`、`iter_limit_hint`、deadline、同一个外借 work 引用与余额全部原样继承，所有已经执行并收费的步不能撤销或退款。Bland 模式、驻留及重入次数也不重领。已有刷新/索引维护计数没有必要为恢复重置；即使需要改变内部维护时点，也必须与资源额度区别说明，第一版保留最小改动。

`rebuild_initial_basis` 只重建表格、逆矩阵、基与人工列，保留当前 `bounds` 和 `row_terms/row_rhs/row_op/row_slack`，因此是可复用的最小冷入口。`prev_bounds` 仍留给下一次正常入口的 swap 机制，不另回填原始模型界。重建后的成本、列布局与原始/割行映射沿现有实现保留。

重要欠账点：重建内部会把 `phase1_pending` 暂清 false。第一版资格要求第一次 Phase-2 失败当时 pending=false，因而不会用冷恢复抹去尚未完成的 Phase-1 欠账。如果调用入口曾 pending=true，但本次已经完整完成 Phase-1 和清理，随后 Phase-2 才数值失败，可以恢复；不能把历史上曾有欠账误当永久禁用条件。重建完成后必须立即令新人工列产生欠账（`phase1_pending = num_art > 0`），再做重建后的期限/额度检查。否则若此时直接返回 TimeLimit，新人工列尚未清理但欠账为 false，之后 resolve 或快照恢复可能错误跳过 Phase-1。也可以统一用一个必定立账的停止收口，但不要只依赖基值碰巧非零让 `basics_violated` 救场。

新人工欠账只由完整 Phase-1 清理成功清除；重建后若无人工列，则没有新人工欠账。不能将旧失败状态当成新可行性证明。重建后预算检查失败时不得定价或换基；检查通过才执行第二次完整两阶段。第二次任何阶段失败原样停止，且 Phase-1 失败保持欠账。

重建本身按既有工作步定义不收费，因为余额计的是实际主元/界翻转；它仍消耗墙钟，所以前后都要检查 deadline。一次重建是有限的矩阵工作，但不能宣称硬实时截止。两次尝试共享同一迭代余额、仅一次重建，既有反循环预算不重领，保证不会由恢复逻辑产生无限循环。

## 为什么第一版只改 Dense

Sparse 的 `numerical_retry_or_fail` 已在非刚重构状态先做一次整基 LU 重因子化及基本值重算，随后重做当前阶段定价、方向和比值；Dense 的 `refresh_values` 不具备这一种从原矩阵重因子化的修复能力。两者恢复机制本就不同。Dense 增加一次失败后的完整冷恢复，不改变数学 LP、容差、入/离基规则或证明出口，只改变“同一剩余额度内是否还能完成证明”。一个引擎完成证明而另一个诚实 LR，不违背同一 LP 语义。

Sparse 再加 cold retry 会涉及更多独立出口：resolve 入口脏因子化失败、`factorization_broken`、对偶主循环的回退链、Devex 重置、人工清理及失败主元的收费口径。尤其 `do_pivot` 可先改变基并扣 work，再因周期重构失败而退出，当前迭代计数的既有口径由专项测试固定。不能只复制 Dense 包装就假定这些状态都闭合。第一版不改其恢复策略，只补准确的契约说明并运行既有双引擎对照；以后再以真实 Sparse 失败证据单独设计。

## 快照、B&B、FFI 与证明诚实性

恢复次数只存在调用栈局部，clone/snapshot 不保存或重领该调用的额度；work 本来是外借状态，也不能被快照复制。重建原地保留当前根割和局部割。B&B 现有快照恢复对累计迭代差额的补账继续生效，因为恢复不清 iterations_total，不另构造对象。

只有第二次新证明成功的结果会作为这一次 LP 的终态交给 B&B；第一次内部数值 Failed 并不是已触发真实资源上限。若真正触限或再次失败，LP 仍返回原诚实停止状态，B&B 仍保存原子树估计、增加未决并保持 limit_hit，完全不改“曾真实触限则 LR”的规则。不得按 incumbent 已支配未决界、显示 obj=bound 或栈已空去清 limit_hit。

所有接口仍是私有实现调整，FFI ABI 仍为 1、状态映射与 panic 边界不变；这不是清理 FFI 错误粘滞状态的许可。必须继续保留有限值、负人工、Phase-2 人工固定零、绝对界及最终解检查；冷恢复不是撤销这些守卫，也不能代替原模型残差与最优值对账。

## 最小测试与验证建议

1. 健康路径与局部资格：同一小 LP 的冷/热求解无故障时不重建，结果、基和计数与旧路径一致；预置旧 diagnostic 后遇到真正迭代上限也不得恢复。Phase-1 数值失败、清理失败和 pending=true 的第二阶段失败均不能进入新恢复。
2. 一次真实失败被恢复：在真实阶段或刷新失败点用仅测试可见、局部清理的故障注入制造一次超界，确认旧严格守卫先拒绝、随后只重建一次、最终解满足当前原约束与界。首轮已执行步骤加第二轮步骤的计数和 work 消耗全部保留；测试不能直接把状态改成 Optimal。
3. 持续失败与终止：两次均注入第二阶段坏值，最终 IterationLimit、objective NaN、仅一次恢复；第二次 Phase-1 溢出或负人工则保留 pending。原有自然 safe-ratio 反例和残人工真实无界/假无界对照必须继续成立。
4. 资源边界：失败恰好用尽 iter_call 或最后一个 work 步时零次重建；尚剩少量额度时第二次沿原限额停止，不重领 1,000/10,000 次；已过期 deadline 零次重建；重建后期限到期时零次第二轮主元且新人工欠账为 true。用确定性测试钩子模拟前/后时点，避免 sleep 与计时竞赛。
5. 当前 LP 保真：附加一个约束最优值确会改变的 cut，并收紧当前 bounds，再注入可恢复故障；与同界、同割的新鲜参考 LP 对比。断言割行数及行映射不变，不能仅比较目标。覆盖恢复后下一次 sibling bounds 的 resolve。
6. 快照作用域：有割的失败状态 clone 后分别恢复/继续，局部恢复资格不粘住，旧人工欠账不被丢弃，快照外 work 不重领。恢复前后的真实累计迭代仍能被现有 B&B 快照补账统计正确收集。
7. 核心守卫测试若此前直接调用两阶段入口并要求“坏基即 LR”，拆分为一次尝试必须拒绝与公开恢复入口重新证明两层断言；不能简单把原测试期望放宽为 Optimal，而不核实新证明、预算和故障次数。

实施者获得 CPU 窗口后先做最小红绿回归与 Dense/Sparse 健康语义对照，再做规定的默认测试和 release 验收，以及预算/期限/快照/诊断组合。实际 lseu 只能用同源 probe 验证是否恢复证明、是否仍出现两次失败、计数和原模型残差是否正确；p0201 的 30s 未证明不能据本设计推断会改善。没有运行这些检查之前，不宣称救回证明或性能通过。

正常路径只增加有限的局部结果判别，不增加每步矩阵扫描；失败路径一次重建大致为 `O(m*(n+m))` 加剩余求解工作。它可能显著增加单个失败节点的成本，也可能避免未决子树导致整树无法证明；两者都必须实测，不能凭两条 lseu 错误记录预先承诺性能收益。
