# 排课联合选值与冲突计分

本轮使用首轮冻结的 140 门课、20 个时段和 8 间教室。每节课要同时避开教师、班级和教室冲突。在完整可行的课表中，以每节课实际时段与偏好时段的绝对差之和衡量质量，越低越好。[冻结算例](../../instances/timetable.txt) · [计算规则](../../cases.py)

## 排课实测

新版 MIC 五次都在构造结束时找到代价为 109 的可行课表。首个可行解的中位用时从 157.80 ms 降至 5.91 ms，约为原来的 1/27。10 秒截止代价中位数从 187 降至 109，降低 41.7%。同轮 OptaPlanner 得到 102，新版 MIC 高 7 点（6.9%）。三个引擎各 5 次都满足全部硬约束。

## 实现

- 在最佳适配构造中，MIC 从硬冲突规则识别由两个变量组成的位置编码，例如「时段 × 教室数 + 教室」。构造一门课时评估完整组合，在同一时段内换教室时复用已算出的时段分数。局部搜索也能让两门课一次交换时段和教室。变量对须互不重叠、低位取值跨度小于进位且总组合至多 1024 个，以限制构造开销。[联合构造与移动](../../../../planner/src/business/search/pairs.rs)
- 对「组内每一对值相等就罚一分」的求和，评分器验证确实覆盖全部配对后记录每个值的占用数。如果已有三门课占用同一位置，再排进去便增加三对冲突。移动一门课只需更新旧、新两个位置的计数。共享的比较表达式若另有用途会继续参与常规评分。缺边、重边、自比较时仍逐项计算。[冲突计分实现](../../../../planner/src/business/score/collisions.rs)

## 如何比较

Apple M4，单求解线程，同一时间只运行一个求解器。旧版 MIC 可执行文件和四组输入均与首轮归档逐一核对指纹。新版直接读取相同的模型文本。OptaPlanner 8.44.0.Final 使用上轮同一份 Java 模型、增量评分器及核心 JAR。每个引擎分别预热两次，每次 2 秒，再按种子轮换出场顺序。5 个正式种子每次都从空课表开始，各给 10 秒。首次可行时间包含求解器内部构造和搜索，输入解析与 JVM 启动在计时区外。首解与截止解都用独立 Python 规则复核。[运行顺序和校验](ab.py) · [机器环境与指纹](results/environment.json)

## 正确性与复现

- 单独替换评分器，用旧版搜索在四种冻结模型上运行种子 7 和 19，每种分别执行 0 步和 300 步。16 组完整输出逐字节相同，包含分配、序列、每条罚分与停止原因。Rust 单测另与全量逐对评分核对 400 次多变量修改与回滚。
- 另用原生成器的排课函数和数据种子 1729、8191 生成两份同规模课表，求解种子均为 7。关闭局部搜索，逐项复算构造结果，旧版在两份课表上都留下 10 对硬冲突，新版都直接构造出可行解，代价分别为 111 和 129。这两份课表只用于检查构造行为。
- 排班、配送、生产排程各取种子 7，两版 MIC 各给 500 ms，六次都找到可行解。新旧版的截止代价分别相同，依次为 330、1468、180。这三项只做回归检查。
- 独立验分覆盖 15 条排课正式记录、6 条预热和 6 条短回归。旧版可在临时副本中还原，19 份源码的指纹与首轮归档吻合，本机重建的可执行文件也与冻结旧版逐字节相同。[还原和复测命令](REBUILD.md)
